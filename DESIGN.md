# Rexter: дизайн системы

Документ описывает сервис в текущем виде: что он делает, из каких компонентов
состоит, как устроены данные и рекомендации. Ранняя версия этого файла
относилась к периоду до PostgreSQL и LightFM; решения, которые с тех пор
изменились, перечислены в разделе 11.

## 1. Задача

Rexter показывает пользователю персональную ленту фильмов. Каталог — MovieLens
32M: 87 585 фильмов, 200 949 пользователей, 32 000 213 оценок. Пользователь
регистрируется, ставит оценки от 0.5 до 5.0 и получает подборку; оценки хранятся
в PostgreSQL и служат сигналом для модели.

В сервис входят:

- сайт на React с лентой, каталогом, поиском и профилем;
- REST API на FastAPI;
- офлайн-обучение LightFM и онлайн-выдача через FAISS;
- загрузка MovieLens, обогащение TMDB и пересчёт статистики;
- конфигурация для VPS: Caddy, systemd, Docker.

Не входят: семантический поиск по описаниям, объяснение рекомендаций, A/B-тесты
и автоматическое переобучение по расписанию.

## 2. Сценарии

**Новый пользователь.** При регистрации интерфейс предлагает оценить несколько
популярных фильмов (`/api/v1/calibration-movies`). Пока оценок нет, лента
собирается из `movie_stats`; после первых оценок профиль считается по векторам
этих фильмов, и лента становится персональной без переобучения модели.

**Прогретый пользователь.** Для пользователя, попавшего в обучение, берётся
готовый вектор из `user_embeddings.npy`. FAISS ищет ближайшие фильмы, из них
собирается лента: 5 лучших и 2 случайных из хвоста топ-100. Показанные фильмы
не повторяются 24 часа.

**Профиль и история.** Пользователь видит свои оценки, статистику по жанрам и
может изменить оценку; повторная запись обновляет существующую пару
`(user_id, movie_id)`, а не создаёт дубликат.

**Поиск.** Поиск идёт по подстроке в названии фильма. Это не семантический
поиск: TF-IDF и эмбеддинги описаний в текущем сервисе не используются.

## 3. Компоненты

```
Браузер
  │  HTML/JS или Vite dev-сервер с прокси
  ▼
FastAPI (uvicorn, 127.0.0.1:8000)
  ├── PostgreSQL: movies, users, ratings, movie_stats
  ├── Redis: показы за 24 часа
  ├── data/artifacts: эмбеддинги, FAISS-индекс, маппинги
  └── frontend/dist: статика в продакшене
```

Офлайн-контур не работает во время запроса:

```
PostgreSQL
  → build_features.py → data/processed/*.npz
  → train_lightfm.py (Linux-контейнер) → data/artifacts/*
  → перезапуск API загружает артефакты
```

`build_features` читает базу курсором asyncpg порциями, поэтому 32 млн оценок
не нужно держать в памяти целиком. Обучение вынесено в контейнер, потому что
LightFM 1.17 на Windows падает в WARP.

## 4. Данные

### 4.1. Схема

| Таблица | Поля |
| --- | --- |
| `movies` | `id` (MovieLens `movieId`), `title`, `year`, `genres`, `country`, `poster_url`, `synopsis`, `director`, `cast_members`, `tmdb_checked_at` |
| `users` | `id`, `username`, `password_hash`, `age`, `gender`, `occupation`, `session_token` |
| `ratings` | `id`, `user_id`, `movie_id`, `score`, `timestamp`; уникальная пара `(user_id, movie_id)` |
| `movie_stats` | materialized view: `movie_id`, `avg_rating`, `ratings_count` |

`ratings.score` — `double precision`, а не целое: шкала MovieLens имеет шаг 0.5,
и округление теряло бы 31% значений. `timestamp` хранится как unix-время; для
оценок из интерфейса это время простановки.

База занимает около 4.3 ГБ. Плотность матрицы оценок — 0.18%.

### 4.2. Загрузка

`load_movielens.py` пишет каталог и оценки через `asyncpg COPY`, а индексы,
`UNIQUE` и внешние ключи на `ratings` создаёт после заливки. Для 32 млн строк
это быстрее, чем поддерживать индексы во время вставки. Флаг
`--reload-ratings` снимает индексы, делает `TRUNCATE`, заливает `ratings.csv`
заново и строит объекты обратно; каталог и TMDB-данные при этом не меняются.

### 4.3. Обогащение TMDB

`enrich_movies.py` полностью асинхронный (`asyncio`, `aiohttp`,
`Semaphore(40)`). Обновление аддитивное: пустое значение из TMDB не затирает
сохранённое, а `movies.title` никогда не подменяется — название остаётся из
`movies.csv`.

Финальный ответ TMDB (200 или 404) записывается в `tmdb_checked_at`, поэтому
`--missing` не запрашивает повторно фильмы, которых на TMDB нет. Сетевые сбои
не отмечаются и подбираются следующим запуском.

Страна производства складывается из `production_countries` и `origin_country`
в `movies.country` — коды ISO 3166-1 через запятую (`US,GB`). Коды устойчивы к
смене локали, а русские подписи для фильтров собираются в
`backend/countries.py`. Колонка появилась позже остальных метаданных, поэтому
`init_db` добавляет её идемпотентным `ALTER TABLE movies ADD COLUMN IF NOT
EXISTS country varchar(120)`, после чего `python -m backend.enrich_movies
--countries` перезапрашивает только фильмы с пустой страной. Исторические коды
TMDB (`SU`, `YU`, `XC`) тоже переводятся.

На текущей базе постеры есть у 85 659 фильмов (97.8%). Оставшиеся 1 926
фильмов остаются в каталоге, но не попадают в ленту, рекомендации и калибровку:
константа `RECOMMENDABLE` в `backend/api.py` и набор `_UNAVAILABLE`, который
движок получает при старте.

### 4.4. Статистика

`movie_stats` — materialized view с уникальным индексом по `movie_id`. Её
обновляет только `python -m backend.refresh_stats`
(`REFRESH MATERIALIZED VIEW CONCURRENTLY`). API не считает агрегаты по
`ratings` на горячем пути: лента читает `movies` и `movie_stats`, а из
`ratings` делает одну индексную выборку — какие фильмы пользователь уже оценил.

## 5. Офлайн-контур

### 5.1. Матрицы

`build_features.py` собирает в `data/processed/`:

| Файл | Размерность | Содержимое |
| --- | --- | --- |
| `interactions.npz` | 200 949 × 87 585 | CSR, значения — оценки |
| `item_features.npz` | 87 585 × 219 302 | multi-hot признаки, 612 925 ненулевых |
| `user_mapping.pkl`, `movie_mapping.pkl` | — | биекция id и внутренних индексов |
| `user_ids.npy`, `movie_ids.npy` | — | те же биекции для обучающего контейнера |

Внешние id не непрерывны (максимум 292 757 при 87 585 фильмах), поэтому обе оси
перенумерованы в `0…N−1`. Обратное преобразование — `index_to_raw` в маппинге
или соответствующий `.npy`.

Признаки фильма гибридные: identity `movie:<id>` запоминает конкретный фильм,
а `genre:*`, `director:*`, `cast:*` позволяют оценить новинку без оценок.
Пропущенное значение заменяется на `<unknown>`, чтобы строка не осталась пустой.

### 5.2. Модель

LightFM, loss WARP, `d=64`, 10 эпох, `learning_rate=0.05`, `item_alpha=user_alpha=1e-6`,
`max_sampled=10`, seed 42. В обучение идут только оценки ≥ 4.0: 15 938 238
взаимодействий из 32 000 213. Обучение занимает около 4–5 минут на 12 ядрах.

WARP выбран вместо предсказания точного рейтинга, потому что задача —
отсортировать каталог, а не угадать число. Оценки ниже порога не считаются
положительными, иначе фильм с оценкой 1.0 тянул бы профиль к себе.

Скор модели:

```
score(u, i) = p_u · q_i + b_u + b_i
```

`q_i = Σ e_f` по признакам фильма, поэтому вектор фильма не хранится отдельно.
`b_i` дописан 65-й координатой вектора фильма, у пользователя там `1.0`;
`b_u` лежит отдельно. Так онлайн-поиск остаётся одним скалярным произведением.
Сверка с `model.predict` даёт расхождение не больше `9.54e-07`.

Пользователи без единой оценки ≥ 4.0 не получают градиента, и LightFM оставляет
им случайный вектор. При экспорте такие строки обнуляются (222 пользователя) —
онлайн-контур видит нулевой вектор и собирает профиль по фактическим оценкам.

### 5.3. Артефакты

| Файл | Размер | Содержимое |
| --- | --- | --- |
| `user_embeddings.npy` | 52 МБ | 200 949 × 65: `p_u` и `1.0` |
| `item_embeddings.npy` | 22 МБ | 87 585 × 65: `q_i` и `b_i` |
| `user_biases.npy` | 0.8 МБ | `b_u` |
| `faiss.index` | 23 МБ | `IndexFlatIP` |
| `user_ids.npy`, `movie_ids.npy` | 2 МБ | обратный маппинг |
| `lightfm_meta.json` | — | параметры, версии, время обучения |

FAISS хранит плоский индекс, а не IVF/HNSW: 87 585 векторов по 65 float32 — это
23 МБ, и точный перебор укладывается в миллисекунды. Векторная БД и
приблизительный поиск здесь не дают выигрыша.

## 6. Онлайн-контур

Один запрос к `/api/v1/feed` или `/recommend/{user_id}`:

1. **Вектор пользователя.** Если пользователь есть в `user_embeddings.npy` и его
   вектор не нулевой — берётся строка из файла. Иначе собирается профиль из
   последних 100 оценок: среднее векторов фильмов с весами `score − 3`,
   нормализованное по L2. Если оценок нет, профиль отсутствует.
2. **Исключения.** Оценённые фильмы (индексная выборка), показанные за 24 часа,
   фильмы без постера и явно переданные `exclude_ids`.
3. **Поиск.** FAISS `IndexFlatIP` возвращает `k = max(500, top_k × 10,
   |исключения| + 100)` кандидатов. Внутреннее произведение, а не косинус: WARP
   обучал именно его, нормализация уничтожила бы выученную длину вектора и
   смещение. Если FAISS недоступен, работает запасной путь на NumPy.

   С фильтрами ленты (`country`, `genre`, `year_from`, `year_to`) API сначала
   выбирает подходящие `movie_id` запросом к `movies`, а движок считает
   скалярное произведение по всем разрешённым векторам и берёт топ уже из этого
   подмножества. FAISS `IndexFlatIP` не поддерживает фильтр по маске; если бы
   фильтровали только верхушку полного поиска, фильм редкой страны мог бы в неё
   не попасть. Перебор 87 585 × 65 занимает единицы миллисекунд.

4. **Отбор.** Из первых 100 подходящих кандидатов берутся лучшие
   (`round(top_k × 5/7)`) и случайные из хвоста — для ленты из 7 карточек это
   5 и 2. Случайность ограничена `seed`, если он передан.
5. **Маппинг.** Индекс → `movie_id` через `movie_ids.npy`, затем один `SELECT`
   по первичному ключу `movies`. Отдельного запроса к `ratings` для агрегатов нет.

Показы записываются в Redis sorted set `rexter:shown:<user_id>` со временем
показа и TTL 24 часа. Если Redis недоступен, используется словарь в памяти
процесса; после перезапуска он пуст, и при нескольких воркерах показы не
разделяются. Кулдаун — оптимизация выдачи, а не гарантия.

Отказы:

- нет артефактов или профиль не строится — лента собирается из `movie_stats`;
- нет Redis — кулдаун уходит в память;
- после фильтрации не осталось кандидатов — тот же популярный fallback;
- битый FAISS-индекс — поиск через NumPy.

Артефакты загружаются в `lifespan` при старте. На Windows индекс читается через
`np.fromfile` и `faiss.deserialize_index`: `faiss.read_index` не открывает путь
с кириллицей. Если индекс не прочитан, сервис стартует, но пишет предупреждение.

## 7. API и доступ

| Группа | Пути |
| --- | --- |
| Служебные | `GET /health`, `GET /api/v1/movies` |
| Аккаунт | `POST /register`, `POST /login`, `POST /logout`, `GET /user/{id}` |
| Оценки | `POST /rate`, `POST /api/v1/rate`, `GET /user/{id}/history` |
| Каталог | `GET /search?query=` |
| Рекомендации | `GET /recommend/{user_id}`, `GET /api/v1/feed`, `GET /api/v1/filters`, `GET /api/v1/calibration-movies` |
| Профиль | `GET /api/v1/profile` |

Действия со своей учётной записью требуют заголовок `X-Session-Token`; токен
выдаётся при регистрации и входе и хранится в `users.session_token`. Пароли —
PBKDF2-HMAC-SHA256, 200 000 итераций, только стандартная библиотека. Вход и
регистрация ограничены 10 попытками в минуту с одного IP (счётчик в памяти
процесса).

Каталог, поиск, лента и рекомендации открыты без токена. Схема создаётся
автоматически при старте; отдельного инструмента миграций нет.

Фронтенд обращается к относительным путям. В разработке Vite проксирует их на
`127.0.0.1:8000`, в продакшене `frontend/dist` раздаёт сам FastAPI, поэтому
CORS нужен только для нестандартной схемы с отдельным доменом
(`REXTER_ALLOWED_ORIGINS`).

## 8. Нефункциональные свойства

- Весь путь запроса асинхронный: SQLAlchemy 2.x + asyncpg, `aiohttp`,
  `redis.asyncio`. SQLite и синхронные драйверы не поддерживаются:
  `database.py` падает при импорте, если схема URL не `postgresql+asyncpg://`.
- Память процесса: около 45 МБ на векторы фильмов и FAISS, 52 МБ на
  user-эмбеддинги через `mmap`, плюс Python и SQLAlchemy. Обучение требует
  заметно больше: матрицы и временные копии CSR.
- Сервис рассчитан на один процесс uvicorn. Кэш авторизации и fallback
  кулдауна живут в памяти; для нескольких воркеров нужен общий Redis и
  внешний rate-limit.
- Старт не зависит от наличия модели: без артефактов сайт работает на
  популярном. Без PostgreSQL сервис не стартует.
- Каталог и оценки меняются только скриптами; API не пишет в `movie_stats`.

## 9. Эксплуатация

Основные переменные окружения: `REXTER_DATABASE_URL`, `REXTER_REDIS_URL`,
`REXTER_COOLDOWN_TTL`, `REXTER_ARTIFACTS_DIR`, `REXTER_ALLOWED_ORIGINS`,
`REXTER_LOG_LEVEL`, `TMDB_API_KEY`. Значения по умолчанию рассчитаны на
`docker-compose.yml`; для VPS используется `.env` (образец — `.env.example`).

При старте в лог пишется строка вида
`Рекомендации готовы: 87 585 фильмов × 65, пользователей — 200 949, поиск — faiss, кулдаун — redis`.
Она подтверждает, что артефакты и Redis подключены, а не сработал fallback.

Типовые операции:

```bash
python -m backend.refresh_stats              # после массовой загрузки оценок
python -m backend.load_movielens --reload-ratings
python -m backend.ml_pipeline.build_features # после изменений каталога
docker run --rm -v "${PWD}:/app" rexter-train \
    python backend/ml_pipeline/train_lightfm.py
```

На Windows перед переобучением API нужно остановить: он держит `.npy` через
`mmap`, и контейнер не сможет перезаписать файлы. Резервная копия базы —
`pg_dump`; пошаговая установка на VPS, systemd и Caddy — в
[deploy/README.md](deploy/README.md).

## 10. Метрики и проверки

Офлайн-метрики ранжирования (`HitRate@K`, `NDCG@K`) пока не считались. Для
корректной оценки нужен разрез по времени: обучение на старых оценках,
проверка на более новых. RMSE для WARP не показателен, потому что модель
оптимизирует порядок, а не значение оценки.

Что проверено на текущей сборке:

- свёрнутые эмбеддинги воспроизводят `model.predict` с точностью `9.54e-07`;
- выдача различается у разных пользователей;
- повторный запрос ленты не пересекается с предыдущим (Redis-кулдаун);
- новый пользователь после нескольких оценок получает персональную ленту без
  оценённых фильмов;
- фильтры страны, жанра и года возвращают только подходящие фильмы, а пустой
  результат не подменяется популярным;
- ни один фильм без постера не попал в выборку из 500 рекомендаций;
- при отсутствии артефактов и Redis сервис продолжает отвечать.

Онлайн-метрики (CTR, конверсия в оценку) не собираются: в интерфейсе нет
событийной аналитики.

## 11. Принятые решения

| Решение | Причина | Ограничение |
| --- | --- | --- |
| Только PostgreSQL, без SQLite | 32 млн строк, COPY, materialized view, индексы после заливки | Нужен Docker или внешний сервер |
| LightFM WARP, а не SVD/PyTorch | Разреженные данные, CPU, гибридные признаки, ранжирующая функция потерь | Старое Cython-расширение, WARP не работает на Windows |
| Обучение в Linux-контейнере | На Windows LightFM 1.17 падает с access violation | Нужен Docker при каждом переобучении |
| FAISS `IndexFlatIP`, без Qdrant | 87 585 векторов — точный поиск быстрый, меньше инфраструктуры | При росте каталога на порядок понадобится ANN |
| Смещения свёрнуты в векторы | Один скалярный продукт на онлайн-поиске | Размерность 65 вместо 64 |
| Порог «понравилось» ≥ 4.0 | Оценка 1.0 не должна считаться положительным сигналом | Часть взаимодействий не участвует в обучении |
| Redis как необязательный кэш | Кулдаун не должен ломать выдачу | Память процесса не переживает перезапуск |
| Фильтры ленты — SQL + NumPy по подмножеству | Точное совпадение без денормализации и без потери редких стран | Сканирование 87 585 строк `movies` на запрос с фильтром |
| Популярное как fallback | Сайт работает до обучения модели | Выдача не персонализирована |
| Старые `ml/`, `app.py`, `run.py` не используются | Исторические эксперименты со Streamlit и SVD | Поддерживаются только для справки |

## 12. Деплой

```
интернет → Caddy (443, HTTPS) → uvicorn 127.0.0.1:8000
                                      ├── PostgreSQL 127.0.0.1:5432 (Docker)
                                      └── Redis 127.0.0.1:6379 (Docker)
```

Caddy получает сертификат автоматически. PostgreSQL и Redis не публикуются
наружу; uvicorn слушает только loopback и работает под systemd с
`MemoryMax=3G`. Статику отдаёт FastAPI, поэтому отдельный веб-сервер для
фронтенда не нужен. Подробности, включая перенос базы дампом и загрузку
артефактов, — в [deploy/README.md](deploy/README.md).

## 13. Ограничения и открытые вопросы

- Метрики ранжирования не измерены; текущая оценка качества — ручная.
- Новые пользователи не попадают в эмбеддинги до переобучения: для них работает
  профиль по оценкам.
- Переобучение запускается вручную; расписания и автоматической проверки
  качества нет.
- Один процесс uvicorn: rate-limit и fallback кулдауна не разделяются между
  воркерами.
- Нет объяснений рекомендаций, A/B-тестов и событийной аналитики.
